# Dye test, 2026-11-08 (measured)

Question: an inlined allocator helper leaves no symbol in the compiled
object; can its compiled copies be found?

Protocol: Linux 6.12.116, mm/slub.c. A 16-byte dye pattern
(D7 1D 5A A5, four times) inserted as the first statement of
slab_alloc_node via asm volatile(".byte ..."); a different 16-byte
control pattern (C0 DE, eight times) in kmem_cache_alloc_noprof.
Build mm/slub.o only (x86_64 defconfig, CONFIG_SLUB=y). Scan the
object bytes for both patterns; check nm for the helper's symbol;
scan a baseline object (scripts/mod/empty.o) built in the same build.

Results: slab_alloc_node has 6 source call sites and no symbol in the
object. Its dye appears 8 times in .text, once per final inlined
expansion, each inside a named wrapper (__kmalloc_noprof,
kmem_cache_alloc_node_noprof, __kmalloc_cache_node_noprof,
__kmalloc_node_track_caller_noprof, __kmalloc_node_noprof,
kmem_cache_alloc_lru_noprof, kmem_cache_alloc_noprof,
__kmalloc_cache_noprof). Control dye: exactly 1. Baseline: 0.
The 8 against 6 is accounted for: one call site sits inside
__do_kmalloc_node, itself always inlined, expanded into three
wrappers (5 + 3 = 8).
