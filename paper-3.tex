\section*{Statement of the Problem}
In the prior two papers, [1] and [2], we have devised a deterministic memory allocation and then shown it able to carry a typical boot-time page load on an embedded version of Debian. In this paper we demonstrate the techniques needed to associate the memory allocations with real random-access memory so that our example, Fubuki, can run actual applications at full speed.

\section{Introduction}
% Status: technique overview inserted at Andrew's direction, 2026-11-08.
% The build and live-run steps are IN PREPARATION or NOT YET RUN;
% see paper-3-composition.md for the evidence label of each step.

Our techniques are applied in the following order, upon the source
code making up Fubuki and upon the built ISO that is the system
under test:

\begin{enumerate}
\item \textbf{The sift.} The kernel source tree is searched
textually for every spelling of the allocator calls, producing a
census of what can be called.
\item \textbf{The control trace.} A recorded boot of Fubuki,
traced from the first instruction available to the tracer, shows
which of those calls the exercised system actually made.
\item \textbf{Reconciliation.} The trace is compared against the
source, and the comparison names the allocator centers: the core
functions the exercised calls pass through.
\item \textbf{The compiled subset.} The source census is reduced
to the subset that Fubuki's own kernel configuration compiles into
the ISO, each patch point marked compiled in, modular, or absent.
\item \textbf{The dye.} A distinctive byte pattern is inserted
into an inlined center and the compiled artifact is scanned for it,
so the inlined copies that leave no symbol are counted where they
actually landed.
\item \textbf{The patch at the centers.} Allocation and free are
redirected at the centers named above, not at individual call
sites. The vmalloc address reservation is left stock; its backing
is the step replaced.
\item \textbf{The translation layer.} Allocations are associated
with real random-access memory: the coordinates the allocator
issues are bound to actual frames, and the inverse binding is run
on free.
\item \textbf{The rebuilt ISO.} The image is rebuilt with the
patched kernel and with a boot service that starts the test
application without an interactive login.
\item \textbf{The automatic boot.} The ISO under test is booted
under QEMU and runs a deterministic page-exercising application at
full speed, which writes its own ledger of requests and releases.
\item \textbf{The audit.} The new trace is reconciled against the
application ledger and against the allocator's own ledger, so that
every event is accounted for by both sides.
\end{enumerate}

\section{Prior Results}
% Status: SETTLED. One paragraph per paper, drafted 2026-11-08 at
% Andrew's direction, awaiting his stet.

In \cite{fine2026iscandar} we constructed a deterministic memory
allocator by formal bijection: an extensible coordinate system is
mapped onto a two dimensional memory map, so that allocation is the
computation of coordinates for a run of exactly the requested size,
and deallocation is the inverse map. At $k=3$ the map covers a cube
of 32,768 sectors. The search is bounded by construction, the
placement is exact fit, and a request that cannot be served is
refused outright, leaving the decision with the caller. The result
is an allocator whose behavior on any sequence of requests is fixed
in advance by the sequence itself.

In \cite{fine2026revisited} we extended the construction from
$k=3$ to $k=4$, composing up to 32 cubes under a beam of 1,048,576
sectors, and subjected the extension to a recorded load rather than
a synthetic one. The complete boot of an embedded Debian system,
Fubuki, was captured from the kernel's own tracepoints: 812,106
allocations. Replayed through the $k=4$ allocator at a calibration
of one sector to one page, the load was carried with no refusals
and no anomalies, at a peak of 56,023 live objects; against a buddy
system control replayed on the same trace, the peak memory granted
differed by a fraction of one percent. The same load was afterwards
carried in an arena of half the size, again with no refusals. Both
results, however, were obtained with the allocator standing apart
from the machine: in the first paper within its own pool, in the
second over a recording. Its allocations had not yet been
associated with the real memory of a running system.

\section{The Census, a Byproduct of Earlier Research}
% Status: MEASURED. Moved out of the Sift section at Andrew's
% direction, 2026-11-08. Andrew confirmed 2026-11-10: the
% section's itemized form is its settled form, and it is in the

The census is the sift's product in durable form: a counted
inventory of every occurrence the pass found, spelling by spelling,
across the 59,969 source and header files of the tree, some ten
million lines. Where the sift is the act of searching, the census
is the record the search leaves behind, and it is the census, not
the search, that the later steps consume: the reconciliation audits
the trace against it, and the compiled subset is a pruning of it.
The census began as a byproduct of earlier research, a planning
count taken during the design work that preceded this paper, and is
promoted here to evidence. \[
\text{\parbox{0.92\textwidth}{\begin{itemize}
\item Its headline figures are these: 77,577 occurrences in the kmalloc family, and 16,559 more across the wider allocator surface.
\item The distribution is sharply skewed.
\item A single free spelling, \texttt{kfree}, accounts for 40,597 occurrences and \texttt{kzalloc} for 21,808, while \texttt{kmem\_cache\_alloc}, the door the recorded boot used most, appears only 329 times in the source.
\item Static abundance and dynamic importance, the census shows at a glance, are different quantities.
\end{itemize}}}
