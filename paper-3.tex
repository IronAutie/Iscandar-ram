\section*{Statement of the Problem}
In the prior two papers, [1] and [2], we have devised a deterministic memory allocation and then shown it able to carry a typical boot-time page load on an embedded version of Debian. In this paper we demonstrate the techniques needed to associate the memory allocations with real random-access memory so that our example, Fubuki, can run actual applications at full speed.

\section{Introduction}
% Status: technique overview inserted at Andrew's direction, 2026-11-08.
% The build and live-run steps are IN PREPARATION or NOT YET RUN;
% see paper-3-composition.md for the evidence label of each step.

Our techniques are applied in the following order, upon the source
code making up Fubuki and upon the built ISO that is the system
under test:

\begin{enumerate}
\item \textbf{The sift.} The kernel source tree is searched
textually for every spelling of the allocator calls, producing a
census of what can be called.
\item \textbf{The control trace.} A recorded boot of Fubuki,
traced from the first instruction available to the tracer, shows
which of those calls the exercised system actually made.
\item \textbf{Reconciliation.} The trace is compared against the
source, and the comparison names the allocator centers: the core
functions the exercised calls pass through.
\item \textbf{The compiled subset.} The source census is reduced
to the subset that Fubuki's own kernel configuration compiles into
the ISO, each patch point marked compiled in, modular, or absent.
\item \textbf{The dye.} A distinctive byte pattern is inserted
into an inlined center and the compiled artifact is scanned for it,
so the inlined copies that leave no symbol are counted where they
actually landed.
\item \textbf{The patch at the centers.} Allocation and free are
redirected at the centers named above, not at individual call
sites. The vmalloc address reservation is left stock; its backing
is the step replaced.
\item \textbf{The translation layer.} Allocations are associated
with real random-access memory: the coordinates the allocator
issues are bound to actual frames, and the inverse binding is run
on free.
\item \textbf{The rebuilt ISO.} The image is rebuilt with the
patched kernel and with a boot service that starts the test
application without an interactive login.
\item \textbf{The automatic boot.} The ISO under test is booted
under QEMU and runs a deterministic page-exercising application at
full speed, which writes its own ledger of requests and releases.
\item \textbf{The audit.} The new trace is reconciled against the
application ledger and against the allocator's own ledger, so that
every event is accounted for by both sides.
\end{enumerate}

\section{Prior Results}
% Status: SETTLED. One paragraph per paper, drafted 2026-11-08 at
% Andrew's direction, awaiting his stet.

In \cite{fine2026iscandar} we constructed a deterministic memory
allocator by formal bijection: an extensible coordinate system is
mapped onto a two dimensional memory map, so that allocation is the
computation of coordinates for a run of exactly the requested size,
and deallocation is the inverse map. At $k=3$ the map covers a cube
of 32,768 sectors. The search is bounded by construction, the
placement is exact fit, and a request that cannot be served is
refused outright, leaving the decision with the caller. The result
is an allocator whose behavior on any sequence of requests is fixed
in advance by the sequence itself.

In \cite{fine2026revisited} we extended the construction from
$k=3$ to $k=4$, composing up to 32 cubes under a beam of 1,048,576
sectors, and subjected the extension to a recorded load rather than
a synthetic one. The complete boot of an embedded Debian system,
Fubuki, was captured from the kernel's own tracepoints: 812,106
allocations. Replayed through the $k=4$ allocator at a calibration
of one sector to one page, the load was carried with no refusals
and no anomalies, at a peak of 56,023 live objects; against a buddy
system control replayed on the same trace, the peak memory granted
differed by a fraction of one percent. The same load was afterwards
carried in an arena of half the size, again with no refusals. Both
results, however, were obtained with the allocator standing apart
from the machine: in the first paper within its own pool, in the
second over a recording. Its allocations had not yet been
associated with the real memory of a running system.

The census is the sift's product in durable form: a counted

across the 59,969 source and header files of the tree, some ten

The census began as a byproduct of earlier research, a planning
count taken during the design work that preceded this paper, and is
promoted here to evidence.
\begin{itemize}
\item Its headline figures are these: 77,577 occurrences in the kmalloc family, and 16,559 more across the wider allocator surface.
\item The distribution is sharply skewed.
\item A single free spelling, \texttt{kfree}, accounts for 40,597 occurrences and \texttt{kzalloc} for 21,808, while \texttt{kmem\_cache\_alloc}, the door the recorded boot used most, appears only 329 times in the source.
\item Static abundance and dynamic importance, the census shows at a glance, are different quantities.
\end{itemize}

\section{The Dye Test}
% Status: MEASURED 2026-11-08 on Linux 6.12.116, mm/slub.o;
% the artifact stands in data/ (dye-test-2026-11-08.md). The
% experiment is the author's, proposed from his experience
% debugging embedded systems. Laid down 2026-11-10 at Andrew's
% direction, in the itemized style of the Sift section, after
% the gates formulation was discussed and approved in chat.

\begin{itemize}
\item It opens with the question the step answers: can a gate be missing between the source and the executable? A gate is a function every request of some family must pass through, and this kernel carries whole pieces of its allocator as code in header files: the kmalloc dispatch is inline logic in a header, and the funnel itself, \texttt{slab\_alloc\_node}, is a static inline helper. Such code leaves no symbol in the compiled artifact, so a symbol audit can neither confirm the gate was compiled nor count the copies the compiler made of it.
\item Then the method, an experiment proposed by the author from experience debugging embedded systems: a distinctive byte pattern, the dye, is planted in the gate's body in the source, emitted so the optimizer cannot delete it, a second pattern is planted as a control in an ordinary non-inlined function, the object is compiled, and the artifact is scanned for both patterns. A gate can be missing outright, the pattern nowhere, or missing in part, fewer copies than the source predicts, which would mean a path that reaches allocation without passing the gate.
\item Then the findings, which locate anything missing down to the least particular, one expansion of one gate: the gate's dye appears 8 times in the object, all in \texttt{.text}, each copy inside a named exported wrapper, against 6 call sites in the source. The excess is accounted for exactly: five sites sit directly in exported wrappers, and the sixth sits inside an inline helper that was itself expanded into three wrappers, so 5 + 3 = 8. The control dye appears exactly once, and a baseline object built from an unmodified file contains neither pattern.
\item Then the boundary, stated in the section rather than apologized for later: the run covers one object file of a defconfig build and boots nothing; its conditions, SLUB built in with SLUB\_TINY unset, are the conditions the compiled subset found in Fubuki's own configuration, so the reading transfers to her build class; and the audit is of the one inlined gate, the remaining centers being named symbols that a symbol audit reaches directly.
\item And it closes with the hand-off: the compiled-artifact leg of the completeness evidence is in hand. The sift reads the source, the trace reads the running system, and the dye reads the artifact, and the three agree on the centers. What remains is the run itself, and the sections turn to it.
\end{itemize}

\section{Automatic Boot and the Page Exerciser}

\begin{itemize}
\item It opens with the question the step answers: how do you run the patched system so that the evidence is complete, repeatable, and untouched by human timing, and so that part of the load is known exactly in advance?
\item Then the arrangement: the patched Fubuki boots unattended under QEMU at 512 MB, with the page tracepoints armed from t=0; a boot service runs the exerciser; and the finish step exports the trace and the exerciser's ledger and shuts the guest down. Two workloads share the boot: the system's own startup, uncontrolled, and the exerciser, controlled to the last allocation.
\item Then the exerciser itself: a fixed program of page allocations in classes from 1 to 128 pages, arranged in phases, a build-up, a partial release that leaves anchors standing, churn cycles that re-allocate exactly what was released, and a final drain to zero. It writes its own ledger as it runs. It opens with a console menu under a 10-second timeout whose default is the standard run, the extended run with more churn standing as the second option, because the evidence boot is unattended and the menu exists for the rehearsals.
\item Then the discipline that gives the step its force: because the program is fixed, a prediction sheet is computed from the program alone before any run, counts, sizes, peak, and end state, and the audit will print predicted against actual. The prediction is never edited after a run; a mismatch is a finding.
\item Then the boundary, stated in the section rather than apologized for later: this step is designed, not yet executed; first rehearsals run in a stand-in guest, and the evidence run uses the ELBE-built Fubuki image, preserving its lineage; and what the exerciser's page-level results will mean under the patched kernel depends on the page-allocator ruling, which remains open.
\item And it closes with the hand-off: the boot produces the trace and the ledger; the audit, the paper's last step, is where they are read against the prediction and against the control.
\end{itemize}

\section{Live Interposition}
% Status: NOT YET BUILT. This section is design only, written
% 2026-11-10 at Andrew's direction after discussion; the build

% his design rulings and the reconciliation run. Standing

\begin{itemize}
\item It opens with the question the step answers: can Iscandar serve a running kernel's requests as they occur, in real time, in place of the allocators the kernel was built with? The earlier papers replayed a recorded trace offline; this step is the live form of the same claim, the allocator interposed between the kernel's callers and the kernel's memory.
\item Then the arrangement, three parts: the patch at the selected centers of section 8; the bridge from the patched system to the Iscandar arena; and the translation layer, which the design places in user space, between the two.
\item Then the translation discipline, the step's spine: Iscandar grants coordinates, not addresses, and the kernel cannot dereference a coordinate, so every grant crosses the bridge twice in its life, forward at allocation, when the coordinate becomes an actual pointer the caller can use, and backward at the free door, when the pointer is translated back and the bijection runs in reverse to return the run.
\item Then the two problems the design records inside this step: the named caches, which carry object size, alignment, and sometimes a constructor, so the design must state how a cache is represented on the Iscandar side before the funnel can serve it; and early boot, since the kernel allocates from its first breath and interposition cannot serve before the arena stands, so either the arena is raised before the first redirected call, or the earliest calls pass through stock and are logged as such. Both stand open at this writing, awaiting the author's rulings.
\item Then the failure semantics: Iscandar refuses the request and the caller decides; it does not get lost, throw, or terminate abnormally. A kernel allocation site already knows how to hear a refusal, a null return being an ordinary event under memory pressure, so the patch maps the refusal onto the kernel's own failure semantics, and no other outcome crosses the bridge.
\item Then the boundary, stated in the section rather than apologized for later: none of this is built yet. The section is a design, and the paper claims for it only that the centers are named, the discipline is stated, and the open problems are recorded as open.
\item And it closes with the hand-off: when this step is built and the boot of section 10 runs on the patched kernel, the measurements that follow are the paper's evidence, and the audit reads them against the prediction and the control.
\end{itemize}

\section{Accomodations for Operating System as an Application}
% Status: written 2026-11-10 at Andrew's direction, recording the
% concessions the PC rig makes in simulating the real system's
% ROM and SRAM, so the claims can be read at their true width.
% Retitled and extended 2026-11-11 at Andrew's direction: the
% extent ledger, the relocated areas, and the compile-time map
% fixtures, from the design session of that day.

\begin{itemize}
\item It opens by naming the situation plainly: the live arrangement of the preceding section runs on a PC, and two of its components are simulations of hardware a real system would carry as parts: read-only memory holding the oracle tables, and static memory holding the arena. The concessions are recorded here so that no reader mistakes the rig for the machine.
\item Then the tables. In a real system the oracle tables reside in ROM or in flash, written once and read forever, as they began in the author's 80188 design, where the tables were ROMs. On the PC they are files mapped read-only by mmap, and the serving code has no write path to them, a rule enforced by the mapping itself, as the ROM enforces it in hardware.
\item Then the arena. In a real system the arena is a static memory chip mapped at a fixed address, and an Iscandar coordinate is an offset into that chip; the mapping never moves. On the PC the arena is raised by mmap and is backed by ordinary pages granted by the page allocator, whose involvement ends at that raise: every grant, placement, and refusal inside the arena is Iscandar's alone.
\item Then the substrate, and the boundary of what was replaced. In the rig the stock page allocator supplies the arena's pages, standing in for the bulk memory a real system presents as a device; it hands the arena over and withdraws, and it parcels nothing for any caller. Its further duties, reclaim, watermarks, and the feeding of the page cache and of user processes, are a PC operating system's virtual-memory duties, not an allocator's charter, and they were never among the things this paper replaces. What the paper replaces is every allocator the kernel names; the substrate is named here so that replacement is not misread as wider, or narrower, than it is.
\item Then what Iscandar is not, stated against its own home ground. An RTOS, the class of system Iscandar was first built for, is not required to provide virtual memory at all: no per-process address spaces, no demand paging, no page cache, no reclaim, and those absences are no defect in it, because its contract never promised them. Iscandar is not a virtual memory replacement and does not attempt one: it translates no addresses and administers no address spaces. Where a virtual memory system exists, as in the kernel under test, it stays, stock and untouched; where none exists, none is missed. Iscandar's whole charter is allocation, the deterministic and exact parcelling of a store of memory, with a refusal when the store cannot serve. Nothing in this paper should be read as claiming more for it than that charter, or less.
\item Then the accommodations the operating system itself exacts, beginning with the length a real pointer destroys. A CPUPointer carries its base and its length in the one word; a real pointer, which is what the kernel's callers hold, carries its base in its offset and the length nowhere. So the arrangement keeps an extent ledger: one bin per page of each cube, and at grant time the length of the grant that starts at that page is stuffed into its bin. Deallocation runs the address math in reverse, cube and start page recovered by division, reads the length back out of the bin, and so completes the CPUPointer the engine's free path requires. The shadows of live grants never collide, because a granted page is never issued again, and so every bin has at most one live writer, by construction. The ledger is no part of Iscandar: in the allocator's original RTOS applications the word circulates whole in the caller's hands, the covenant intact, and no ledger exists or is needed. It is part of the price of supporting a full operating system, charged to this paper's setting and to nothing else.
\item Then where that price is paid: inside the store itself, in the manner of the author's 80188 design, where the arena tables were relocated into the beginning of the SRAM and their sectors and counts marked manually. Each cube carries one relocated area at its head, standing at the cube's base address in the simulated SRAM, which is the SRAM base plus the cube's number times a cube's span, the correspondence being arithmetic throughout. The area is pre-allocated at the raise, before serving begins, and its sectors and counts are marked by hand, so the cube's books open already balanced. It holds the cube's slice of the extent ledger, sixteen pages, and the cube's maps and counters, three pages: nineteen pages of the cube's 32,768, 76 pages of the arena's 131,072, so the served capacity stands net at 130,996 pages. One area per cube, and nothing of a cube's fixture in another cube's space, so that a severe failure in a cube is diagnosed from that cube's one area, in a single reading.
\item Then the fixtures of the machine. The translation layer's own working memory, which cannot be taken from the doors it serves without closing a circle, and the bridge channel between the patched kernel and the layer, which lives in neither side's allocation, are not found at runtime and not negotiated at boot. Both stand reserved in Fubuki's compile-time memory map, at the addresses the build states, so that a mismatch between the patch and the map fails the build rather than the boot. The arrangement is thereby specific to this build and its map; the specificity is recorded here, with the reserved sizes, as one of the accommodations, and porting the arrangement to another kernel means drawing that kernel's map the same way.
\item Then what the concessions preserve: a fixed mapping, read-only tables, uniform lookup, exact-fit grants, and the refusal semantics. These are the properties on which the paper's claims about correctness and freedom from panic rest, and the simulation preserves each of them.
\item Then what they do not preserve: timing. Pages of DRAM behind a mapping do not behave as static memory behaves, and no figure in the Measurements is an SRAM figure. Speed is reported there as record, and bears on the verdict only by contributing to a panic, as the Discussion fixes.
\item And it closes with the width of the claim, stated once: the paper's conclusions concern allocation behavior, which the simulation preserves entire. It draws no conclusion about hardware timing, which the simulation does not preserve at all.
\end{itemize}

\section{Discussion}
% Status: criterion fixed in advance (2026-11-10); verdict left blank until the live run is measured.

\begin{itemize}
\item It opens by fixing the criterion in advance, before any run exists to be judged: the main criterion is whether this is a direct replacement, and whether it runs without a panic.
\item Then it defines direct replacement strictly: same kernel, same configuration, same boot, same workload, the allocators exchanged at the centers and nothing else altered to make the exchange survivable. Any exemption, if one is forced on us, is named, and the claim shrinks to fit it.
\item Then it fixes what the replacement is: the C transcription of the engine, not the Python model. The Python code serves only to generate the oracle outputs against which the C is admitted; no Python runs in the serving arrangement. A run served by the Python model would therefore not meet the direct replacement criterion, whatever its other results.
\item Then the second half: the patched system boots unattended, reaches the finish step, the exerciser completes, the evidence exports, and the guest shuts down clean, no panic, no oops, no invariant violation. A panic ends the claim for that run outright; it is not averaged into anything.
\item Then the subordinate quantities, placed where they belong: speed and paging coverage are reported in the Measurements and discussed here only as record, and either can affect the verdict only by contributing to a panic. The paper does not grade the run on them.
\item Then what a pass would mean, stated modestly in advance: the claim of the first two papers, support by replay, would become support in place, for this kernel, this configuration, and this workload, and no wider.
\item And it closes with the verdict left blank, deliberately: this section will be completed from the run's record, and not before.
\end{itemize}
